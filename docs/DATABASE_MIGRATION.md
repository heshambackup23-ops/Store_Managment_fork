# نقل MySQL إلى D1

الترحيلات التنفيذية في `cloud/api/migrations`. استخدمنا `INTEGER` للمعرفات والمال بوحدات صغرى، و`TEXT` لبيانات UTF-8 والتواريخ، ومفاتيح خارجية وفهارس للحركات. تبقى بيانات النظام في Laravel خارج بيانات الأعمال المراد ترحيلها.

| جداول MySQL | اعتماد المصدر والوجهة |
|---|---|
| `categories`, `products`, `customers` | الجداول المقابلة تحافظ على IDs. يربط `products.category_id` بالتصنيف. رصيد افتتاحي في `inventory_movements`، ويُعاد رفع الصور منفصلة. |
| `invoices`, `sales`, `sales_items`, `payments`, `debts` | فواتير وبنود ومدفوعات ومرتجعات في D1. يجب تحليل `invoices.items` والحقول القديمة للمنتج الواحد وتسوية المبيعات التي تظهر في أكثر من جدول قبل التحويل. |
| `installments`, `personal_debts`, `personal_debt_payments` | يُراجع ارتباط الفاتورة والقسط والعميل والمنتج، وتُطابق قيم الأصل والمدفوع والمتبقي لكل سجل. |
| `suppliers`, `purchases`, `supplier_payments` | اعتماد المورد قبل الشراء والدفع. قد توجد دفعة معلقة بلا شراء محدد وتحتاج قاعدة تخصيص معتمدة. |
| `wallets`, `wallet_transactions`, `wallet_expenses`, `wallet_cash_adjustments`, `wallet_audit_logs` | اعتماد المحفظة والعميل والمستخدم ومراجع الحركة السابقة. يلزم إثبات تطابق رصيد المزود والصندوق والذمم وإدخالات العكس. |
| `damaged_items`, `maintenances` | الهالك يحتاج منتجًا ومستخدمًا حسب السجل. الصيانة تحتفظ بهوية الطلب وسجل الحالة والمدفوعات حين تتوفر. |
| `users`, `profiles`, `roles`, `permissions` والجداول الوسيطة | إنشاء حسابات جديدة ومواءمة صلاحيات معتمدة، مع الاحتفاظ بجدول ربط IDs قبل إسناد الحركات التاريخية. كلمات المرور والتوكنات تُعاد تهيئتها. |
| `settings`, `app_notifications`, `notification_reads`, `backup_logs`, `api_idempotency_records` | تُراجع الإعدادات والإشعارات وهوية القراء. مفاتيح المحاولة القديمة وسجلات النسخ لها أرشيف منفصل عن جلسات D1. |
| جلسات Laravel، رموز Sanctum، طوابير العمل والتخزين المؤقت | سجلات تشغيل مرتبطة بالبيئة الأصلية. |

## أداة الكتالوج والعملاء

تقبل `cloud/api/scripts/import-laravel-catalog.mjs` ملف JSON بالتنسيق `henra-mysql-catalog-v1` مع كائن `tables`، أو NDJSON أقدم ذي الرأس `store-management-backup-ndjson` الإصدار 1. يُمرر السعر `DECIMAL` كنص مثل `"42.35"`. يجب تصدير التواريخ مع إزاحتها. الخيار `--mysql-utc` مخصص لمصدر ثُبت أن قيمه بلا إزاحة تعبّر عن UTC. استخدم IDs الخاصة بالمصدر كما هي.

```sh
cd cloud/api
node scripts/import-laravel-catalog.mjs fixtures/mysql-catalog.synthetic.json
mkdir -p imports
node scripts/import-laravel-catalog.mjs fixtures/mysql-catalog.synthetic.json --actor-id 1 --emit-sql imports/catalog.generated.sql
npx wrangler d1 execute DB --local --file imports/catalog.generated.sql
```

شغّل الترحيلات وأنشئ المستخدم المشار إليه قبل الاستيراد. التنفيذ الجاف يعيد تشغيل SQL مرتين على SQLite مع ترحيلات D1 ويقارن الصفوف والمخزون والأسعار ويفحص المفاتيح الخارجية. SQL المولّد مخصص لقاعدة تجربة محلية فارغة بعد التهيئة. راجع عدد الصور والوحدات المباعة تاريخيًا في التقرير؛ لا تدخل هذه القيم في سجل افتتاح الكتالوج. أداة الكتالوج ترفض ملفًا يضم صفوفًا مالية أو تشغيلية خارج نطاقها.

## استلام نسخة تشغيل مستقبلًا

1. اعزل نسخة MySQL معتمدة وحافظ على النسخة ووقت أخذها وتجزئتها. اعمل على نسخة محلية مؤقتة. صدّر كل جدول بقيمة `DECIMAL` نصية ومعرفات غير مقربة.
2. اعتمد طريقة تسوية الفواتير التاريخية والمحافظ والأقساط ومراجع العملاء قبل بناء تحويلها. احفظ المعرفات وخرائط المفاتيح ومعرف المصدر لكل حركة وافصل تاريخ الإنشاء عن تاريخ العملية.
3. طابق الصفوف والمفاتيح الخارجية، ووحدات المخزون لكل منتج، ودفعات كل فاتورة وقسط، وذمم الموردين، وأرصدة المحافظ والصندوق. نفّذ الاستعادة في قاعدة منفصلة قبل التفكير في ترحيل معتمد.
4. احتفظ بتقرير فروق موقع عليه وتحقق من إعادة التشغيل ومن النتيجة تحت D1 قبل أي انتقال تشغيلي. تظل نسخة العرض مخصصة للبيانات الاصطناعية.

## ترحيل الديون الشخصية ودفعاتها

يشغّل `node scripts/import-laravel-personal-debts.mjs fixtures/mysql-personal-debts.synthetic.json` من `cloud/api` تجربة على SQLite. يقبل التنسيق `hilal-mysql-personal-debts-v1` بجدولي `personal_debts` و`personal_debt_payments` فقط. احتفظ بالمعرّفات الأصلية والمبالغ العشرية النصية والتوقيت مع إزاحة صريحة. يحوّل المستحق للدائن إلى `payable`، ويرفض أي صف يختلف متبقيه عن أصل الدين بعد طرح دفعاته، ويتحقق من التطابق بعد تشغيل الاستيراد مرتين.

يعيّن `--actor-id` معرف مسؤول الترحيل في الوجهة، ويبيّن التقرير عدد معرفات منفذي المصدر التي استُبدلت به. احتفظ ببيانات المصدر لإثبات هوية منفذي الدفعات التاريخية. استخدم `--emit-sql imports/debts.generated.sql` بعد مراجعة التقرير، وطبّقه على D1 معزولة تستخدم الترحيلات الحالية. يحجز الاستيراد نطاق المعرفات في سجل العمليات حتى تبدأ المعاملات اللاحقة بعد آخر معرف مستورد. يحتاج نقل الفواتير والموردين والمحافظ والأقساط التاريخية إلى تحويل وتسوية منفصلين.
